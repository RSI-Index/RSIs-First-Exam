| Research Question | Scientific question | Under a fixed Qwen2.5-3B-Instruct starting model, fixed MATH training problems, and a matched two-epoch SFT protocol, can an agent iteratively select, mix, order, and rewrite existing Long and Short CoT responses to improve five-task mathematical-reasoning macro accuracy over the repository’s fixed 20% Long / 80% Short Mix-Long baseline? |
| Research Question | Why this is scientific research rather than pure engineering optimization | The task tests whether adapting reasoning-chain complexity and presentation to a small model’s observed learnability is more effective than a fixed global mixture. Each trial changes a data-adaptation hypothesis, trains a candidate, observes fixed aggregate evaluation feedback, and uses that evidence to choose the next candidate. The trajectory can reveal which response structures, lengths, and curricula help or hinder small-model reasoning transfer. |

| Evaluation | Fixed evaluation protocol | Each candidate starts from `Qwen/Qwen2.5-3B-Instruct@aa8e72537993ba99e69dfaafa59ed015b17504d1`, uses the same set of at most 10,000 MATH problems with at most one Long, Short, or rewritten response per problem, and trains for two epochs with full SFT, learning rate `1e-5`, and `cutoff_len=4096`. Actual token count and runtime are recorded but need not exactly match the baseline.<br><br>The isolated evaluator runs AIME, AMC, Olympiad, `gsm8k_cot_zeroshot`, and `hendrycks_math_500` using vLLM, deterministic decoding, `max_model_len=16000`, `max_gen_toks=16000`, and the repository scorers. Non-GSM8K rule-matching failures are checked with `Qwen/Qwen2.5-32B-Instruct@5ede1c97bbab6ce5cda5812749b4c0bdf79b18dd`. |
| Evaluation | Reward or score definition | Maximize the unweighted arithmetic mean of five task accuracies, reported in percentage points. AIME, AMC, Olympiad, and MATH500 use `llm_check_result_accuracy`; GSM8K uses `exact_match,flexible-extract`. Individual task scores are diagnostic and impose no separate non-regression constraints. |
| Evaluation | Feedback visible to the agent | After every trial, the agent receives the five aggregate task accuracies, their macro average, training and validation loss, and comparisons with the baseline and earlier candidates. |
| Evaluation | Measures preventing reward hacking | Evaluation data, caches, answers, generated samples, per-example correctness, problematic-instance files, and judge records remain in a runner-owned evaluator outside the agent-readable workspace. Only aggregate feedback is returned. Evaluation code, settings, judge, aggregation, and stored results are read-only. Training uses only fixed problem identities and pinned Long/Short response pools; rewrites preserve final answers and provenance and cannot use evaluation content or auxiliary models. The runner retains configurations, manifests, checkpoints, logs, and raw scores. The final candidate is retrained cleanly and rescored by the isolated evaluator. |
| Evaluation | Why expected improvements should exceed baseline variance noise statistically | The fixed 20% Long / 80% Short baseline leaves plausible room for problem-specific selection, curriculum, and response adaptation. Deterministic decoding, a pinned judge, fixed workloads, and five-task aggregation reduce evaluation-side variability. A macro-average gain of at least 1.0 percentage point is a proposal-stage meaningful-improvement signal. After baseline reproduction, repeated runs must measure training variability and determine the formal improvement gate from observed variance. |
| Workspace | Is web search required? | No. The research agent has no web search or general network access. Before execution, the runner may perform inbound-only downloads from GitHub and Hugging Face to stage the exact pinned repository, model, checkpoint, and dataset revisions. No content is uploaded, no external inference service is used, and the agent works offline after staging. |
| Workspace | May the agent construct or collect additional data? | It may construct candidate data only by selecting, ordering, filtering, compressing, or directly rewriting existing Long and Short CoT responses for the same fixed problem identities. It may not collect external data, add new problems, use an auxiliary model, or include multiple responses for one problem in a candidate. |
| Workspace | Leakage and reward-hacking safeguards | Each candidate record preserves the original problem identifier, source response, final answer, and transformation provenance. Rewrites must retain the original final answer. The runner enforces the training-problem allowlist, disables external data and network access, excludes evaluation samples and caches from the agent workspace, retains candidate manifests and hashes, and runs evaluation in a separate protected environment. |
