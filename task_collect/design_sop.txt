step1: 根据我的project list给你的project， 去扒拉官方实际的代码库，之后所有信息和task设计都统一只看代码库 不参考paper结果
（project 选择标准1. 完全开源 2. 有名 3. 偏向于科学性 而非工程性 4. gpu跑得起 ）

完全按照作者这个代码库开源的设定，任何可以完全使用作者的开源代码库的方案 优先走代码库 不管paper，所有题目的设计也基于代码库不要基于paper，只参考开源代码库的信息作为输入和baseline。

step2: 只通过看代码库来思考哪些实验可以拆出来做成autoresearch类型的task（参考autolab，对一个实验agent多次迭代优化某个指标），可以进行优化 beat 作者的代码库里的方案 （可以有多个实验拆出来做成多个task）。确保最后设计出来的autoresearch的优化task 是科学上make sense的。（拆出来的实验必须在仓库有baseline！）
题目设计尽量避免工程的搜索参数，而是有research含金量的项目找出来，科学研究价值高，有科学意义 和灵魂 的题目
常见的踩坑问题： 
agent action space： 尽可能合理的多给model action的空间，但也要明确agent的边界来保证task 设计的科学性，
reward matric: 是否agent 的提升改进 相比metric本身多次测试的variance 是有明显统计区分。
reward hack： 可能reward hack的地方需要明确禁止了 写在policy里面
是否这个环境要web-search（应当尽量不需要web-search，如果一定要 则需要设计防止reward hack的办法）
evaluation set 集是否agent能看到， 有时可能需要拿error analysis 给feedback，有时完全不能让agent看到，这个要仔细斟酌。


step3: 通过代码库的官方设置来估算gpu使用量，尤其要估算的是跑一次目标实验（一次实验对应single run， 迭代优化对应多次实验run）需要的h100个数和时间。如果能找到适合8卡以内，single run 12h以内能跑完的task，都可以直接进。超过这个卡/runtime的要专人来review，主要关心是否增加更多卡可以加速 减少实验跑的时间。同时应当思考 是否agent explore可以有early stop signal，不必要每次都跑完整个single run，来增加explore的效率和科学性。 

step4: 这些东西sketch好了之后审计代码库 并跑一次该实验复现，得到reference result。如果本身的代码库过于难跑无法跑出来实验结果那么可以不要这个env。跑出来的实验结果可以和paper本身claim的结果比较， 如果不同也没关系 默认用我们复现的。这一次跑不要改实验设置，只能调整涉及硬件的 或者你把代码跑起来的方式
note： 复现实验用卡 大概率要debug很多次才能跑起来。不修改实验本身的setup的前提下 可以加卡改下实现来加速

step5: 跑了一次复现实验之后我来看结果，然后确认我们用不用这个环境。这个时候你要详细和我说清楚task setup是什么（说完整不要漏东西让我去猜，设置和代码库一模一样吗。代码库本身能复现什么，设计的autoresearch task具体是什么，justify你的设计为什么是这样），有什么实际真实的科学发现价值（这个很重要），和仓库claim的结果是否有显著不同，以及为什么。 根据选出来的这个实验，然后输出一个完整的harbour格式, 具体的harbour task的格式我们已经定了。



step6：human review了完整的task之后，会使用agent跑这个harbour task，得到实际的agent优化迭代的结果。
然后我们来看 agent是否真的迭代优化 产生了实际有科学意义的结果，推动了科学发展的向前。是否这是好的环境和task，以及是否需要修改setup。我们也根据agent这次跑的时间来定整个task的gpu hour budget和run time budget


（一个参考的harness运行方式:异步 harness——agent 提交训练后退出,Harbor 每 30 分钟模型轮询,训练终态才唤醒同一个 agent session 继续。）
